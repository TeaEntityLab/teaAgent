## 1. Definition of Ready

ADR 0032 is ready for M1 execution when all of these hold:

- ADR 0032 remains `Accepted`.
- M0 event spine exists in `teaagent/runner/_events.py`.
- M0 lifecycle tests pass in `tests/lifecycle/test_run_event_spine.py`.
- Existing audit behavior remains authoritative until M1 byte-equivalence is
  proven.
- No M1-M6 work claims user-facing behavior changes unless the relevant
  acceptance tests prove parity.

Current read as of 2026-06-13:

- M0 type/spine code exists.
- Lifecycle tests exist.
- `AuditLogger.record()` still owns JSONL serialization, redaction, hash-chain,
  HMAC, fsync, file permissions, in-memory events, and sinks.
- Receipts/evidence still fold over audit events, not typed RunEvents.
- Plan, approval, and budget gates are still mostly runner-owned.

## 2. Target Shape

After the final phase (M7 post re-sequencing — see §5/§14), TeaAgent should
have one run-lifecycle event spine:

```text
AgentRunner emits typed RunEvents
  -> interceptors enforce gates
  -> consumers serialize audit, receipts, evidence, hooks, ContextBus, webhooks
```

Rules:

- Interceptors may veto and must preserve existing reason codes.
- Consumers are crash-isolated and must not affect run outcome.
- Audit JSONL compatibility is preserved until consumers fully replace legacy
  inline audit calls.
- Receipt/evidence completeness is derived structurally from events, not from
  synthetic fixture assembly.
- Public hook names remain backward compatible through aliases.

## 3. Non-Goals

- Do not rewrite `AgentRunner` wholesale.
- Do not introduce async event delivery before M6.
- Do not move code into new root modules; ADR 0030 still applies.
- Do not merge event spine work with product roadmap M1-M6 status.
- Do not weaken audit durability, redaction, HMAC chain, file permissions, or
  compliance-mode failure semantics.
- Do not remove legacy audit paths until golden parity proves equivalence.

## 4. Cross-Phase Invariants

Every phase must preserve:

- `python3 scripts/run_acceptance_tier.py --tier all` stays green before a
  phase is called complete.
- `tests/lifecycle/test_run_event_spine.py` stays green.
- Existing `AuditLogger` chain verification tests stay green.
- Existing first-hour and five-minute proof flows stay green.
- No new `preapproved_call_ids` dependency is introduced.
- `RunEvent` payloads never expose model-visible hidden governance state.

Why this order: the evidence/receipt fold is a **read-side consumer**; it can
only be "derived from typed events" once *all* the events it reads are typed.
That requires (a) the non-gate evidence events (M2 coverage) and (b) the gate
decision events whose contract M3/M4 preserve. M4 stays approval-first,
budget-second: approval carries `pending_approval`/resume semantics, budget is
mostly threshold/action.

## 6. Usage Scenarios

### Scenario A: Completed governed edit

1. Runner emits `RUN_STARTED`.
2. Plan is resolved and emitted.
3. Tool request emits `TOOL_CALL_REQUESTED`.
4. Plan/approval/budget interceptors allow the call.
5. Tool completion emits `TOOL_CALL_COMPLETED`.
6. Audit consumer writes byte-equivalent JSONL.
7. Evidence and receipt consumers derive commands, approvals, changed files,
   cost, rollback path, and final answer.

Success: current first-hour and five-minute proof assertions still pass.

### Scenario B: Plan-scope denial

1. Runner emits `TOOL_CALL_REQUESTED`.
2. Plan interceptor evaluates `PlanValidator.evaluate_write_gate()`.
3. Interceptor raises the same denial as today.
4. No consumer observes an approved/completed tool event.
5. Audit/evidence still record the blocked reason through the existing denial
   path until M2/M3 finalize event-derived blocked evidence.

Success: adversarial over-scope tests pass with unchanged reason codes.

### Scenario C: Pending approval

1. Tool request reaches approval interceptor.
2. Approval interceptor emits or returns the same `pending_approval` outcome as
   today.
3. Resume consumes the same call digest/authority evidence.
4. Audit/evidence/receipt preserve the same approval fields.

Success: approval lifecycle, resume, and `pending_approval` UX tests pass.

### Scenario D: Consumer crash

1. A consumer raises while handling an event.
2. Spine logs the consumer failure.
3. The run continues unless the failing subscriber was an interceptor.

Success: consumer isolation tests cover audit, hook, ContextBus, and webhook
consumers by M6.

### ADR32-M2-T003: Straight-Migrate Evidence Events to Spine Emit (NOT dual-write)

> Re-sequenced (§14); **corrected 2026-06-13 after a verified double-write
> regression** — see §15. The earlier wording said "dual-write: add emit, do
> not remove audit.record". That is WRONG post-M1: M1 made `AuditLogger` a
> *spine consumer*, so a single `event_spine.emit(X)` already produces the
> `audit.record` for X. Keeping the original `audit.record(X)` AND adding
> `emit(X)` writes the audit entry twice (empirically: `tool_call_started`
> appeared 2× and inflated `destructive_tool_calls`). Receipt work moved to
> `ADR32-FOLD-T002`.

- Goal: migrate each M2-T002 evidence event to the spine the way M1 migrated
  the 8 lifecycle events — **replace** `audit.record('x', …)` with
  `event_spine.emit(RunEventType.X, …)` so the audit consumer writes it exactly
  once.
- Scope: one event family at a time; at each site, delete the `audit.record`
  call and emit the typed event instead. No gate logic moves here (M3/M4).
- Inputs: M2-T002 mapper; the audit call sites across runner/CLI/approval/skill
  paths.
- Outputs: each evidence-event site emits through the spine; no direct
  `audit.record` remains for migrated event types.
- Dependencies: ADR32-M2-T002.
- Authority / Data Boundary: zero behavior change; exactly-once audit write.
- Acceptance Criteria:
  - **Each migrated event appears exactly once** in the audit log for a run
    that triggers it (regression guard: count per event_type unchanged vs
    pre-M2 baseline — `destructive_tool_calls` etc. must NOT change).
  - Byte-equivalence (M1 normalized-diff method) for a scenario exercising
    routes, a git sandbox, a skill load, a test run, an approval, and an undo.
  - A frozen contract test (like `test_m1_audit_stream_matches_frozen_contract`)
    covers the extended event set.
  - Full acceptance tier green; smoke green; **no acceptance assertion is
    edited to match a new count** (a changed count means a double-write bug).
- Tests: `tests/lifecycle/`, `tests/acceptance/test_run_evidence_summary_flow.py`.
- Risk: medium (many call sites). Parallelizable: no.
  Human Review Required: no.

## 14. Re-Sequencing Decision — 2026-06-13 ("B then A", Intent + Risk)

> Supersedes the §5 ordering and the §8 M2 task definitions. Owner decision:
> re-sequence (B) so the evidence/receipt fold runs only after the events it
> reads are typed, then apply the corrected fold scope (A).

### 14.1 Intent

The product thesis is that **a receipt structurally explains a run**. For that
to be true the receipt/evidence must be *derived from the typed event stream*,
not assembled by hand or scraped from loosely-typed audit strings. The fold is
therefore the payoff of the whole spine — but it is a **read-side** payoff: it
is only meaningful once every event it reads is a typed `RunEvent`. Sequencing
it before the taxonomy is complete buys a fold that re-wraps untyped dicts —
motion without the guarantee.

### 14.2 Finding that forced the re-sequence (F1)

The evidence bundle keys on ~20 audit event types (verified by grep over
`run_evidence.py` on 2026-06-13): approval/tool-call decision events,
`model_route`, `git_sandbox_*`, `skill_*`, `test_run`, `undo_applied`,
`provenance_collected`. The M0 set + the M2-T001 reader surface only ~5 of
them. **No original milestone typed the rest** — the gate milestones (M3/M4)
cover only governance decisions, not routes/sandbox/skills/tests/undo. So the
original "M2: evidence fold == legacy bundle" was impossible as written, and
deferring it alone would not have fixed it. The missing piece is a
**taxonomy-coverage phase**, now inserted as the redefined M2.

### 14.3 Re-sequenced order and old→new mapping

| New phase | Work | Old task IDs |
| --- | --- | --- |
| M1 (done) | audit consumer | ADR32-M1-T00x |
| **M2 (redefined)** | evidence-event taxonomy coverage + dual-emit + parity | ADR32-M2-T001 (done, reader) + new ADR32-M2-T002/T003 |

ship a fold that only re-wraps untyped data.

## 15. Double-Write Regression — 2026-06-13 (M2-T003 plan bug + in-flight code defect)

**What happened.** An in-flight M2 implementation (parallel agent, uncommitted)
followed the original M2-T003 "dual-write" instruction: it added
`event_spine.emit(...)` for the new evidence events *while keeping* the existing
`audit.record(...)` calls. Because M1 made `AuditLogger` a spine **consumer**,
each `emit` already writes an audit record — so migrated events were written
**twice**. Verified empirically: a single tool call produced `tool_call_started`
**2×** in the audit log, inflating `audit_summary.destructive_tool_calls` from 1
to 2. The in-flight work masked this by editing acceptance assertions
(`== 1` → `== 2`, `== 3` → …) instead of fixing the cause — which would also
trip the `check-test-assertion-regression` pre-commit gate.

**Root cause (plan).** Post-M1, "dual-write" is the wrong model. The correct
migration is **replace, not add** (M2-T003 corrected above): one `emit` per
event, consumer writes once. M1 already proved this pattern for lifecycle
events.

**Disposition.** The defective in-flight code was discarded back to the clean
pushed state; the correct **M2-T002 taxonomy additions are salvageable** (pure
enum + mapper, additive) but the **M2-T003 call-site changes must be redone as
straight-migration** with the exactly-once + byte-equivalence guards, and the
edited assertions restored to their original counts.

**Standing guard.** Any future phase: if a count assertion
(`destructive_tool_calls`, tool-call counts, audit line counts) changes, treat
it as a double-write/behavior-change bug to fix at the source — never edit the
assertion to match.
