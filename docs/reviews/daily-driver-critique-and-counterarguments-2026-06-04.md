# Daily-Driver Critique and Counterarguments - 2026-06-04

## Purpose

This document is the skeptical companion to the roadmap. It asks what could be wrong with the current direction, which assumptions are weak, and which alternatives deserve explicit rejection instead of quiet neglect.

## What Could Be Wrong

### 1. We may be over-investing in governance language

TeaAgent may already be safe enough for its current audience, and the documentation could be making the project look more mature than the live surfaces actually are.

**Counterargument**

- The repository contains real governance primitives and real trust gaps.
- The docs are not inventing the problem; they are exposing it.

**Open question**

- Which governance claims are truly product value, and which are just defensive language?

### 2. We may be optimizing for maintainers instead of users

It is possible that the docs corpus is becoming easier for maintainers to manage while remaining too heavy for a new daily user.

**Counterargument**

- Several docs explicitly call for a short current-status front door.
- The existence of a dense corpus is not a mistake if the entry points stay light.

**Open question**

- How many users ever read the deeper analysis, and which guides do they actually follow?

### 3. We may be over-indexing on competitor comparison

There is a risk that the roadmap becomes reactive: Pi does this, OpenCode does that, Claude Code does this, Codex does that, so TeaAgent must respond to all of it.

**Counterargument**

- Competitor surveys are useful only when they identify durable user expectations.
- The point is not to copy competitors. It is to learn the market shape.

**Open question**

- Which competitor features are baseline expectations, and which are just local style?

### 4. We may be under-valuing simplicity

The project may become so intent on receipts, gates, and evidence that the simplest useful workflows become harder than they should be.

**Counterargument**

- The repository already shows user demand for calm, accurate daily surfaces.
- Simplicity is not the same as omission. Honest state can still be simple.

**Open question**

- Which receipts are essential, and which are too expensive for the common path?

### 5. We may be treating docs as a substitute for runtime proof

The bigger the documentation effort, the easier it is to feel progress without fixing the live path.

**Counterargument**

- The docs explicitly warn against this.
- New docs should only exist when they convert ambiguity into work.

**Open question**

- Are we writing more evidence, or just more commentary?

## Alternatives Rejected

### Alternative A: Aggressive feature expansion

Rejected because it would widen the surface before trust drift is closed.

### Alternative B: Aggressive docs deletion and consolidation

Rejected because historical evidence is still valuable and many docs are intentionally dated records.

### Alternative C: Full redesign around a new agent framework

Rejected because the project already has a clear harness identity and the cost of adding another framework would likely be duplication, not clarity.

### Alternative D: Follow one competitor wholesale

Rejected because TeaAgent's differentiation depends on combining malleability with stronger governance, not inheriting one competitor's entire philosophy.

## Signals That Would Invalidate The Current Direction

1. The daily-driver trust gaps disappear and new users still do not find the project useful.
2. The docs corpus keeps growing but acceptance coverage and runtime parity do not improve.
3. Users consistently prefer a simpler workflow over the more governed one.
4. Competitor features converge so strongly that TeaAgent's unique positioning stops mattering.

## What The Critique Implies

- Keep challenging whether every new document earns its place.
- Make sure the roadmap turns into tasks, not just better prose.
- Watch for places where "governance" becomes a synonym for "more complexity".
- Treat simplicity as a design constraint, not an afterthought.
