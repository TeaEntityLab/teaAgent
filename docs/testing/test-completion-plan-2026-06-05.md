## Dispatch Decision

- **Mode:** Implementation plus governance documentation.
- **Strictness:** L3 now, L4 for security/audit remediation.
- **Primary workflow:** Reflective implementation with review gates.
- **Human review:** Required before turning strict mode into a default CI failure.
- **Current CI posture:** Report mode by default; strict mode is available for trial runs and future ratcheting.

## Design Corrections Already Applied

1. `collect_pytest_nodes()` now uses the active Python interpreter instead of hard-coded `python3`.
2. Pytest node parsing now preserves class-based and parametrized node IDs instead of truncating to the file or class.
3. Single-file audit targets now get AST-scanned instead of reporting zero files.
4. The audit now detects:
   - `placeholder`
   - `no_assertions`
   - `mock_only`
   - `construction_only`
   - `undocumented_skip`
5. Exception-boundary tests using `pytest.raises`, `pytest.warns`, and `pytest.deprecated_call` now count as behavior assertions.
6. JSON output now includes inferred `domain`, inferred `tier`, documented skip count, high-risk file count, placeholder file count, and construction-only file count.
7. `--fail-on severe` is implemented and can be used as a future CI gate.
8. `validate_docs_consistency.py` exposes `--test-quality-mode {report,strict,off}`:
   - `report` is the default rollout mode.
   - `strict` fails on weak tests.
   - `off` is local/debug-only and should not be a normal CI path.
9. Pytest collection is required in both `report` and `strict` modes so import/collection failures cannot be hidden by report-only rollout.

## Open Risks

1. **False positives:** Construction-only detection is intentionally simple and may flag some tests that are legitimate smoke checks.
2. **Baseline shock:** Turning strict mode on too early would fail the existing suite because historical weak tests are real.
3. **Over-testing implementation details:** Fixes must assert user/security behavior, not private helper structure.
4. **TUI brittleness:** Headless TUI tests need stable state assertions rather than terminal pixel assumptions.
5. **Agent-mode nondeterminism:** Use deterministic adapters and temporary workspaces; avoid live model calls in default CI.

## Next Concrete Step

Start with the seven P0 security/audit no-assertion files. For each test function with zero assertions:

1. Identify the intended threat or regression.
2. Add at least one assertion on a security boundary, audit event, denial reason, or user-visible failure.
3. Run that file's tests.
4. Re-run the audit and update the snapshot.
5. Only then consider strict-mode CI ratcheting.
